# Local Falcon SAB Scale-First SOP v3.1

Consolidated replacement • Usage-optimized normal operation

This procedure replaces the previous SOP in full. When Matt designates it for a run, it is the sole procedural authority together with his explicit instructions for that run. It applies general rules only; earlier amendments, remembered workflows, research-note wording and past case rulings do not establish current policy. No new paid run is authorized by this revision. Production use requires the matching connector and CRM contract to be deployed and verified; release verification is separate from this document.

Purpose: identify relevant service-area businesses, verify a usable contact, establish credible visibility evidence and prepare a clean CRM handoff. Keep pre-outreach research focused; deeper qualification belongs after a response. Website/platform/service-page audits, review audits, routine review-recency analysis, Reviews Docs, manual Secretary of State research and sales-priority scoring are outside this workflow. Sending-domain setup, warmup, bounce handling and campaign execution are downstream controls, required before scale outreach but not performed by this collection SOP.

## 1. Ownership and authorization

One Codex orchestrator owns intake, research, centering, scan decisions, reconciliation and final handoff. Do not use subagents or delegate run work unless Matt explicitly authorizes delegation for that run. There is no separate supervisor or nested review loop.

The exact Sheet URL and tab are immutable run identifiers. Use the Viva SAB Workflow connector for company-row reads and writes; do not repoint environment variables, rely on a default Sheet or use generic Drive editing for these rows. Require a successful write receipt before claiming a save. Execution batches share one run and SOP; they do not create separate policies or audit loops.

Use the guarded connector. Initialize one run per Workflow Sheet with the orchestrator identity, authorization reference, credit ceiling and the current Google Doc ID/revision of this SOP. Read the SOP in full once at initialization. Check its revision metadata before later stages and reread it only if the revision changes; persist the new revision before continuing. At intake, obtain and store one run-wide authorization to use verified, publicly listed business phone numbers as exact-phone Google search queries for the contact-research fallback. It applies to every company in the run and does not authorize outreach, non-public numbers or personal numbers not publicly presented as business contact information. If absent, complete the other free paths and hold only the exact-phone fallback. Record each exact batch plan before submission: company, Place ID, role, type, center and derivation, centering/corroboration evidence, grid, radius, units, keyword, platform, grid-point count, estimated credits, duplicate-report check and reason. Include any prerequisite save-location action explicitly for the exact Place ID. Never save or alter a location, launch a campaign or change account data without authorization established by the run and guarded connector.

Preserve exact Place-ID deduplication, idempotency, spending limits and durable submission receipts. No direct paid API calls, approval resets or guessed completion. A claim stranded at `preparing_location` may continue automatically under its existing approval only when the connector verifies the exact unchanged authorization, envelope, idempotency key and credit reservation and proves the paid scan request never started through the absence of `submit_started_at`; this is continuation of the approved submission, not a retry or new charge. Record and report the submitted report key immediately. Pending or slow processing is not failure. When submitted reports remain pending, use the connector’s server-side completion monitor at five-minute intervals. Do not have Codex repeatedly poll, resubmit a scan, pause for routine approval or return the task for manual resumption. Continue any safe unrelated work while monitoring runs. When reports complete, automatically verify their exact envelopes, classify them, persist the results and resume the workflow. Notify Matt only for a genuine ambiguity, policy exception, monitor failure requiring action or the final CRM import preview. If server-side monitoring is unavailable, use compact, bounded checks with increasing backoff and automatic delayed continuation. A claim at `submitting`, `ambiguous_response` or any state where the paid provider request may have started remains stopped until the guarded recovery verifies the provider history and satisfies the applicable explicit-approval rule. Recover the existing claim without resetting the run. Retry only after confirmed provider failure and fresh explicit approval. Read-only work and ordinary corrections may continue within scope without repeated permission; paid enrichment remains subject to the approved run scope and cost accounting.

Continue autonomously through routine research, deterministic routing, authorized paid work, classification, reconciliation and manifest construction. Do not request routine scan-batch approvals. Limit each paid execution batch to at most 15 scans and fully reconcile it before starting the next batch. After each completed batch, return a concise non-blocking summary for every scan: company, Local Falcon report URL, specification, measured result and classification, proposed next step and reason, and SOP rule; then continue automatically. List genuine exceptions separately and hold only affected companies while safe unaffected work continues. At other stage boundaries, return aggregate counts plus exceptions. Stop only for a genuine policy/identity/evidence conflict, a provider submission whose duplicate-charge safety cannot be proved, a requested exclusion or discretionary exception requiring Matt, an exceeded authorization/budget, or the final CRM import confirmation. Do not return complete company histories or raw grids unless needed to resolve an exception.

When Matt disagrees, classify the issue: agent error means the current rule was applied incorrectly; a flawed SOP rule needs a proposed general correction and approval. Correct the appropriate layer. Never silently turn a case-specific decision into general policy.

## 2. Discovery, qualification and focused research

Matt configures and runs the master discovery scan: practical market center, suitable tracked anchor, sufficient edge coverage and overlap only when one grid cannot reasonably cover the market. Never change the anchor business's GBP information. Matt supplies the completed report, market/state, trade, exact keyword, run authorization, credit budget, any explicit trade exceptions and supplemental duplicate sources. The assistant does not launch or replace a master scan.

Verify completion, readability, market and keyword. Record master report identity, anchor name/Place ID, center, grid, radius/unit, platform, keyword, expected coverage and actual or estimated credits when available. If identity is unresolved, ask for the correct link rather than generating another report.

Call create_sab_workflow_from_master_report once for the exact report key. Preserve the source discovery snapshot and complete ledger server-side, one row per unique Place ID; never retransmit the full competitor population through chat or create_sab_workflow. Reconcile source-business count, unique/missing/duplicate Place-ID counts, CRM duplicate counts, disposition counts, Sheet row count and Place-ID checksum, explicitly accounting for any tracked-anchor exclusion. A preservation/count mismatch stops downstream work until reconciled. Use check_crm_local_falcon_report only for a read-only diagnostic when no Sheet is being created; check_crm_place_ids is for small supplemental lists, not transferring a master roster.

Every ledger row retains identity, name, rating/reviews, categories, SAB status, available phone/website, CRM duplicate provenance, stage statuses and final disposition/reason; source grid evidence stays server-side. No lead may disappear. Set workflow to scale_first_v2 and upgrade older Sheets to the current structured schema before using new fields. Required artifacts are the discovery snapshot/ledger, connector-backed Workflow Sheet, exact-ID enrichment receipts, verified contacts and separate rejected-candidate evidence, center/authorization/scan records, one validated batch.json, import preview and funnel reconciliation. No Batch Launch Prompts Doc or Reviews Docs is required.

Deduplicate against both deliverable and CRM-only records by exact Place-ID equality before enrichment or scans; never substitute name, phone, email, website, address or fuzzy matching. An existing exact-ID match is excluded unless Matt explicitly approves reprocessing. Preserve distinct Place IDs; do not merge related listings without his ruling.

Request the applicable category, address, rating, review-count, phone and website fields in the server-side master read. The first categories entry is the GBP primary category. Confirm SAB only from address:false; any full or partial public address fails the SAB filter and is discarded, not persisted. Require at least one Google review and rating ≥4.5. Missing/nonnumeric values require resolution, not a pass. There is no other review minimum, no maximum and no standing recency gate. A narrow activity check is permitted only at Matt's request or because specific evidence creates genuine doubt; low review volume alone is insufficient. Do not routinely call the reviews endpoint.

Exclude national/multistate franchises and branded branch networks; local multi-location ownership alone is not an exclusion. Consolidate ambiguous ownership for Matt. The default trade rule requires a primary-category match. Secondary categories or broad services cannot override a clear mismatch unless Matt approves a broader run definition. Defer contradictory or ambiguous relevance; retain the exact primary category and decision evidence. Final trade relevance must be settled before paid scans.

Use enrich_sab_businesses only for survivors of inexpensive filters. Deduplicate inputs before provider requests. My Business Info Live requests use keyword place_id:<exact ID>, location_name and language_code, not a standalone place_id field. Verify exact returned-ID equality before saving. Do not use name-plus-market fallback while exact-ID lookup is available; a documented connector outage is the only fallback basis, and exact returned-ID verification still applies.

Retain compact business name, Place ID, CID, phone, website, rating/reviews, primary/additional categories and stable IDs, services summary, description, is_claimed, coordinates and place_topics when returned, plus actual cost/task receipts. Save business_profile with source=dataforseo_my_business_info_live and the matched compact business fields through the supported workflow/CRM contract; never copy full service objects or noisy raw provider payloads. Source-phone evidence does not resolve a conflicting verified contact automatically; record the verified resolution before export/outreach. A zero-cost response with no task/result is request_not_submitted, not a lookup or charge. Isolate failed/ambiguous enrichment to that company and retry or defer without repeating successful requests. Categories describe Google's taxonomy; services and descriptions describe the company's claims. Use both to assess specialist versus generalist relevance and inform concise outreach context. Profile richness and is_claimed do not prove activity; Business Info provides neither an email nor newest-review verification.

Perform focused browser research individually for each exact Place ID, normally about 15–40 seconds per ordinary company and longer only when the evidence requires it. First search the complete GBP name verbatim and unquoted, followed only by email; retain suffixes and service descriptors. Wait for the rendered results and AI Overview, normally at least five seconds, then visually inspect the AI answer when present and the visible first-page snippets. Text extraction, previously assembled URLs, notes, bulk normalization and connector audits supplement but never replace this rendered inspection.

Inspect the verified company website when available: Contact, About, header/footer and another clearly linked contact-bearing page only when relevant. Inspect company-controlled profiles surfaced on the first results page or directly linked from the verified website when they appear likely to contain contact information. These may include Facebook About/contact information, Instagram bio/contact information, a LinkedIn company page, YouTube About, X/Twitter, TikTok, a Nextdoor Business Page, Houzz or another demonstrably business-maintained profile. Control and exact-company identity—not the platform name—determine classification. Do not search separately for every possible platform.

If no email passes a gate, search the exact verified public business phone alone, without added words, and repeat the rendered AI Overview/first-page inspection. Inspect any newly surfaced relevant official website or controlled profile. This query is also the primary address-discovery query, but contact evidence and address-corroboration evidence remain separate dimensions.

Use independent sources only when needed to verify a candidate or resolve a conflict. BBB, Yelp, chambers and trade associations, licensing directories, Angi, HomeAdvisor, Thumbtack, non-controlled Nextdoor references, vendors, partners, local directories and press may corroborate identity but must never be labelled company-controlled. An email passes only when (1) its domain matches the verified company website; (2) its source contains the exact verified business phone after digits-only normalization; (3) a free-mail address appears on a verified company-controlled website or profile; or (4) multiple independent sources connect that same email to the exact company and verified phone. Company name plus market alone is insufficient. Multiple weak sources never cure a direct phone, domain, ownership or identity contradiction. Reject every failed candidate with its reason; never construct an email pattern or send a test message.

Stop immediately when an email passes a gate; do not continue merely to accumulate sources. Email Ready requires the retained verified email and matching accepted evidence. Needs Email requires a verified public business phone, null email, and genuine exhaustion: the exact-name and authorized exact-phone searches were rendered and visually inspected; the verified website was inspected or its absence documented; every relevant surfaced or linked controlled profile received an inspection disposition; any independent evidence needed for a candidate or conflict was resolved; rejected candidates have reasons; and no unverified email remains.

Attempt each relevant source once through the normal browser path. A source-access failure is a technical limitation, never proof that no email exists, and must not be repeatedly retried during the same run. Hold the contact decision only when the inaccessible source is material to resolving an email or identity conflict; failure of an unrelated or clearly irrelevant page does not block completion.

Persist contact research only through the dedicated single-company `record_sab_contact_research` action after that company's browser work is complete. Generic and bulk company saves may not create or replace contact evidence. In one compact record, retain the exact queries, rendered-results and first-page confirmation, AI Overview present/absent status, official-website disposition, controlled-profile inspections, independent-source inspections, accepted gate or rejected candidates, exact URLs/source types, identity and applicable phone matches, and inspection times. Google search-result pages are search evidence, never official websites or company-controlled profiles. The connector validates sequence and evidence consistency but does not independently prove source truth. One final compact audit returns aggregate totals and exceptions only. Do not build the manifest while any qualified record lacks a valid Email Ready or Needs Email outcome.

Retain a phone returned by Local Falcon or DataForSEO and resolve conflicts before outreach. Owner name is an optional verified nonempty string or null: collect only an explicitly identified owner/founder/managing member as a byproduct, never delay the run or infer ownership from an employee, registered agent, organizer, reviewer or reply signer. Missing owner or email alone is not a blocker. Without either verified contact, do not scan or export; do not invent a Contact Blocked tag or priority score.

## 3. Evidence, privacy and center definitions

Structured run state, eligibility_state, decision_state, qualification_reason and outcome are authoritative. eligibility_state records pre-scan eligibility and may authorize a paid plan; qualification_status is a separate final disposition and remains null while scan work is in progress. Record source report, evidence hash, rule IDs, selected coordinates, derivation, validation status, next action and recenter count. Notes support history only. Use stage-specific compact reads by default and full histories only for conflicts. Use guarded bulk writes where available; each company remains independently validated and one failed row must not roll back successful rows. Use ordinary per-row receipts during work. For completed scan batches use the concise normal-mode summary above; for other stages use one exception-only audit with aggregate counts. Repeat source/evidence inspection only when a conflict, missing receipt or changed state appears.

Before master centering/planning, call analyze_sab_master_centers with the exact completed report key and surviving Place IDs. Reconcile requested/found/missing counts and each missing ID, ranked-cell count/hash, exact geometry, row/column spread and cluster diagnostics. Resolve extraction failure, missing identity or checksum inconsistency before affected centering or spending. get_sab_ranked_cells is a targeted exception/verification tool, not a replacement for master reconciliation. Do not transcribe raw cells, reconstruct server results from chat, or substitute screenshot/proxy footprints. Historical five-cell and two-ring trust labels are not current policy; S01 governs bounded versus genuinely truncated evidence.

If disconnected master-scan clusters do not match an existing deterministic route, hold the company for evidence review; do not invent a center or launch a scan.

Verify completed provider status, exact report key/subject, scan specification and complete grid geometry before decisions. Use server-side extraction and compact diagnostics. Exact ranked evidence means integer ranks 1–20; ranks above 20, 20+ and unknown/unranked placeholders never enter centering, cluster, coverage or peak calculations. For saturation medians only, include every grid cell: retain exact positive ranks, and count 20+/unranked as 21, a worse-than-20 sentinel, never an observed rank. Compute the full 49-cell, outer 24-cell and central 9-cell medians separately. Keep raw ARP for policy tests and all-point ATRP for prospect-facing average position.

When the initial center remains unreliable, address corroboration is required before an auxiliary unless an approved centering rule already resolves the center. A bounded interior point source/coherent cluster does not require unnecessary address research. For an unresolved auxiliary route, complete the focused phone-anchored search and record either an evaluated fit decision or genuine no-candidate research; lack of research is not failed corroboration.

An independently discovered address is a temporary candidate, never a fact to publish. Use phone-anchored results, company-controlled contact/footer/About pages or verified directory, trade-association or licensing records. Require exact-phone, company-controlled publication or independent consistent identity evidence. Residential, suite or mail-receiving type alone is not grounds for rejection: the defensible center is the point Google associates with the listing, not an assumed operating yard.

For each candidate, use record_sab_address_corroboration, which calls evaluate_sab_address_candidate with the exact completed report key/Place ID and ephemeral candidate. Apply the complete-distribution fit decision using the centroid, spread, nearest pin, strongest cluster and truthful geocoder precision. Retain the approximately three-mile fit limit and absence of shape contradiction; proximity to one stray pin is insufficient. The evaluator measures evidence; it does not determine business identity or make the final fit judgment. Record source type, identity method, fit rationale/distances, report/hash and accepted coordinates in decision_state.address_corroboration. An accepted fit can establish corroborated_address regardless of ranked-cell count. If an already reliable centroid conflicts with an address, reject the stale address and retain the centroid; do not buy an auxiliary solely because of that conflict.

Unavailable evaluation, partial geocoding, missing exact Place ID or irreconcilable evidence holds only the affected company. These are incomplete/technical-failure outcomes, never rejected-address/no-candidate evidence and never automatic permission for an auxiliary. Resolve the failure before advancing that route. Retry a technical writer failure only through `record_sab_address_corroboration`; it must freshly verify the same current report and evidence before replacing the hold with an accepted/rejected candidate or completed no-candidate result. A partial known candidate remains incomplete and cannot be relabelled as no candidate. A completed rejected fit or completed no-candidate search may support the applicable S01 auxiliary plan.

Hidden street addresses must not enter the ledger, Sheets, manifests, CRM, notes, chat, handoffs, previews, reports or outreach. Use a raw candidate only within active orchestrator-controlled corroboration; persist safe fit metadata and coordinates, never the address or raw grid. Correct any privacy breach before export or handoff. Every CRM/export address is exactly Service Area Business; never replace it with a research address or market location.

Adjacent cells share an edge or corner (eight neighbors). A coherent cluster contains at least two exact top-20 cells connected under that adjacency rule. A dominant peak is at least three ranks better than the median exact pin. Form best+2 contiguous clusters containing a globally best pin. Choose greatest total 1/rank weight, then nearest cluster centroid to the prior center, then northernmost and westernmost cell. Among tied best pins, choose nearest prior center, then row and column.

When the current central 3×3 contains a coherent cluster, an off-center peak may trigger recentering only when all three tests pass: its selected best pin is at least three ranks better than the best central pin; the 3×3 centered on the selected peak pin has a better median than the current central 3×3; and the candidate 3×3 contains at least as many exact top-20 pins as the current central 3×3. For these neighborhood medians only, assign 20+ and unranked cells the computational sentinel 21; never persist 21 as an observed rank. If any test fails, retain the existing center as unsupported_off_center_peak unless S05 independently requires a different route. If the selected peak's 3×3 extends beyond the scan grid, do not infer missing ranks; apply the existing higher-priority boundary rule. This safeguard does not apply when the current central 3×3 has no exact top-20 visibility or no coherent cluster; use the existing point-source and boundary routes.

Peak targeting applies to the first post-auxiliary deliverable and every recenter. Use the selected peak cluster’s 1/rank centroid when dominant. Otherwise a whole-field centroid is allowed only if it does not move away from the selected best pin and remains within one diagonal cell of the chosen cluster on the proposed 7×7/3-mile grid (√2 miles). If either check fails, use the selected best pin. A recenter must produce verified movement toward that peak; never submit the unchanged center as a recenter.

## 4. Scan decision table

Precedence: authorization/privacy, valid evidence and required corroboration first; apply the current stage only. On auxiliaries, exclusion precedes visibility disposition. On three-mile deliverables/recenters, assess saturation before margin/recentering; a supported off-center peak fails centering under S04/S07. A five-mile comparison preserves the already validated three-mile center: assess S09 and, absent an approved exclusion, apply S08 without another centering test. S09 never validates a center. Proposed exclusions pause for Matt before any final disposition. Routine paid work uses the stored run authorization and guarded preflight, with no more than 15 scans in one execution batch. Standard deliverable: Google 7×7/3 miles, exact run keyword. Routine auxiliaries: scout 9×9/6 miles or justified fine scan 7×7/1.5 miles. Permit one auxiliary and one routine recenter per lead; additional attempts need an explicit exception. Permit at most one five-mile comparison per lead.

| Rule / stage | Evidence | Required action |
| --- | --- | --- |
| S01 — Master | One connected exact top-20 interior cluster; outermost boundary empty. | Use its 1/rank centroid. A bounded point source is sufficient; edge proximity alone does not require a scout. |
| S01 — Truncated master | Exact top-20 evidence touches the actual outer boundary; required corroboration completed without an accepted address. | Scout from a server-calculated three-mile offset from the weighted centroid toward the nearest occupied edge. Adjacent-edge ties use a normalized diagonal, not three miles per axis. Store master_edge_offset. Unresolved opposing ties, absent evidence or incomplete corroboration require resolution; do not guess. |
| S01 — Sparse interior | Two to four disconnected interior pins; required corroboration completed without an accepted address. | Use one 7×7/1.5-mile fine scan at their weighted centroid when the full spread is ≤3 miles. If farther apart, target the deterministic best pin and hold the other islands for an explicit exception. |
| S02 — Wide-scout exclusion | Completed 9×9/6-mile auxiliary: top-20 coverage ≥75%, raw ARP ≤4 AND SoLV ≥60. | All three tests must pass. Record exclusion pending Matt’s checkpoint approval; only then finalize existing_visibility_too_strong. Missing required metrics need evidence review. |
| S03 / S04 — Auxiliary | Completed valid auxiliary, after S02. | Any exact rank 1–20 confirms visibility: plan a peak-targeted 7×7/3-mile deliverable. Scout boundary occupation does not block it. Zero exact top-20 pins alone produces no_visibility_core_found and CRM-only handling. |
| S06 — Saturation first | 7×7: ≥45/49 exact top-20 cells; all-cell median ≤3; outer-ring median ≤ central-3×3 median +2; no supported off-center peak. | Include unranked cells in all medians as defined above. Saturation alone permits the same-center 7×7/5-mile comparison without a recenter exception. |
| S05 — Deliverable margin | Global best pin on boundary, or a maintained/improving outward path. | A qualifying path has ≥3 adjacent pins, starts in a best+2 cluster containing a global best pin, moves strictly closer to the boundary each step, never worsens in rank and reaches it. When the global-best pin is unique and lies within the central 3×3, record such a path as directional visibility extension and retain the validated center. A global-best boundary pin, tied global-best evidence outside the central 3×3 or a displaced selected peak may still fail centering. Two adjacent boundary pins within best+5 alone do not prove failure. Ordinary falloff is acceptable. |
| S04 / S07 — Recenter | S05 independently fails, or an off-center peak passes the three central-contrast, neighborhood-median and exact top-20 support tests above. An incomplete candidate 3×3 uses the existing boundary route; a current center without a coherent cluster uses the existing point-source route. | Permit one peak-targeted routine recenter. If the neighborhood safeguard applies and any test fails, retain the center as unsupported_off_center_peak. Further attempts require an explicit exception. If no supported movement exists, resolve evidence rather than submitting another scan. |
| S08 — Optional comparison and canonical selection | A completed validated 7×7/3-mile report permits one same-center 7×7/5-mile comparison within the authorized run scope, including but not limited to S06 saturation. Same exact Place ID, keyword, platform and grid; only radius changes. | Do not recenter, invalidate the three-mile center or widen again from comparison results. After S09 review, select five miles only when raw unrounded ARP increases AND SoLV decreases. Either tie or failed condition retains three miles. Preserve both reports and the selected report's actual specification/metrics. |
| S09 — Five-mile exclusion | Completed 7×7/5-mile only: ≥45/49 exact top-20 cells, raw ARP ≤3.0 AND SoLV ≥75.0. | All three tests are required. Propose exclusion and wait for Matt. Do not substitute ATRP, validate a center from exclusion, or compare strength across specifications. |

master_edge_offset is an auxiliary launch coordinate, never a validated business/deliverable center. ranked_peak_recentered was already supported; retain it for an evidenced peak-derived center. A planned center or saved report key alone is not validation. Corroborated-address and fine-scan routes must carry their own structured source/fit evidence and exact authorized specification; they cannot bypass S02–S09.

Judge ordinary centering from the distribution and selected peak, not an ARP/ATRP/SoLV cutoff. There is no additional minimum-rank threshold. A modest centered peak with acceptable falloff is valid; stop rather than buying scans to hunt a better rank. Auxiliary routes are measurement labels, not lower prospect classes. Never compare company strength across different specifications, including auxiliary versus deliverable or different canonical radii. Geography, population, appearance and subjective sales-story preference do not alter S08.

Before each paid submission, run `preflight_sab_local_falcon_batch` for the complete proposed execution batch of no more than 15 scans. It reads the live usable-credit balance, saved-location state and pending/completed provider history without submitting scans or writing provider/workflow state. It must compare exact Place ID, keyword, platform, grid, radius, measurement and center, and return plan-bound `duplicate_report_checks` with an evidence reference and check time. Do not submit an equivalent completed report or pending scan. This provider-history search is separate from CRM deduplication and durable request idempotency; neither substitutes for it. Routine browser inspection is unnecessary when the guarded preflight succeeds; use manual read-only reconciliation only when the preflight returns conflicting or incomplete evidence. The plan must match the structured preflight evidence.

## 5. Records, one-file export and import

Deliverable outcome: persist the validated canonical report, actual 7×7 radius, center/derivation, scan date, keyword and verified provider public URL; never derive public URLs from report keys. Preserve raw ARP for S08 and policy tests. Prospect-facing Average Google Maps Position always uses all-point ATRP, including unranked points as supplied/verified by the provider; never substitute raw ARP. Display 20+ when ATRP is ≥20; keep SoLV separate.

Persist proposed center/type together as planned, without inventing a completed scan, report key or history entry. First deliverable completion confirms or supersedes the planned center while retaining it in history. Preserve every prior center, report key, auxiliary role, recenter rationale, authorization and noncanonical variation; never overwrite history manually. Correct a stale type together with its unchanged center and retain the correction evidence. save_sab_scan_result requires the actual role, raw ARP, SoLV, report key/public URL, scan date and keyword; include known center/type/specification and all-point ATRP, never competitor data. For comparison retain both specifications, both raw unrounded ARP/SoLV pairs, both strict test results, selected canonical key and unselected variation.

Once final centers are settled, batch reverse_geocode_sab_centers with exact coordinates keyed by Place ID/company. Write city/state/ZIP only from complete results. Do not infer ZIPs or substitute nearby businesses, research/GBP addresses or the master market. Resolve incomplete results without guessing. A valid center may fall across a state boundary; that alone is not disqualifying. The market source is the validated scan center, not a published business address.

CRM-only outcome: after a valid auxiliary has zero exact top-20 pins, retain its source report/evidence and reverse-geocode the auxiliary scan center solely as market_reference_only. Store source=auxiliary_scan_reverse_geocode, coordinates, city/state/ZIP and the actual auxiliary report key/public URL. These describe the searched market, not a validated business center. The record has no deliverable report, report date, ARP/ATRP/SoLV, validated center or heatmap. Missing reference geography requires resolution without guessing. Verified contacts, the compact business profile and all other qualification rules still apply. Preserve actual auxiliary measurements in source history, never as fabricated prospect deliverable metrics.

Pre-scan eligibility requires confirmed SAB, ≥1 review, rating ≥4.5, exact-ID deduplication or approved reprocessing, franchise/trade eligibility and a verified email or phone. Record those gates in eligibility_state before spending; do not mark the company qualified merely to authorize a scan. Final qualification additionally requires a completed valid deliverable or an approved no_visibility_core_found path. Keep qualification_status null and workflow status in progress while that work remains. Record qualified for a completed pass; disqualified for a mandatory-filter failure; deferred only as a nonterminal recovery queue for intentionally postponed work or material ambiguity; blocked for a genuine identity/access/connector problem or the required pending-exclusion review. Every disposition has a concise structured reason. Do not add website, review-recency, owner-name or sales-priority requirements.

Before export, finish the full run reconciliation. Every discovered Place ID has a structured disposition. Assigned, in-progress, blocked and deferred survivors are nonterminal; deferred is a recovery queue, not evidence that the run is finished. Continue free research, connector recovery and deterministic routing until each survivor is qualified and ready/imported, deterministically disqualified, or Matt explicitly approves that named company as a terminal deferral. Technical failures, tooling gaps, unresolved centering and evidence gaps never become terminal merely because work paused. The guarded terminal-deferral transition records Matt's company-specific approval and creates no general policy.

Build exactly one batch.json through build_sab_run_manifest containing every eligible qualified row at complete OR qa_ready across all execution batches, including CRM-only leads. The manifest builder must fail closed and list every unresolved survivor unless the unresolved count is zero or each remaining deferred company has Matt's recorded named terminal approval. Do not filter only qa_ready. Exclude disqualified, approved terminal deferrals, blocked, imported and unqualified records. Validate the entire manifest against the current scale_first_v2 contract, exact uniqueness, contact tags and recorded scan specifications, then pin its SHA-256 and compact exact-Place-ID/report expectation in run state. Rebuild only when authoritative source data changes. Before or after import, reconcile that exact pinned hash in one guarded read against CRM Place IDs, tags, Service Area Business addresses, prior-send history and workflow import status; return aggregate counts and exceptions only. No competitors.json or competitor sidecar.

Use only supported manifest fields: identity, verified contacts/tag, website, optional verified owner, compact business_profile, qualification and the appropriate deliverable or market-reference fields. Keep rejected emails and operational research outside the manifest, associated by run ID and Place ID. Enrichment history is stored as structured import-provenance metadata; it does not establish eligibility or current scan state from note wording. Preserve supplied phone/profile fields and resolve contact contradictions before outreach. A 5-mile canonical report carries its explicit per-prospect specification override within the same batch; the batch default remains 3 miles. If approved reprocessing finds an existing exact Place ID, attach the report as a variation to that lead rather than duplicating it.

The CRM accepts the one batch.json by paste or file selection. An optional ZIP may contain that same manifest and documented heatmap fallbacks; ZIP packaging is not required. Official heatmaps are retrieved by selected report key. Supply image files only when official retrieval is unavailable and document that fallback; never create a competitor sidecar.

Import preview retrieves and verifies official unaltered heatmap bytes only for deliverables and clearly labels CRM-only entries as having no validated scan/report. Matt reviews the complete preview, duplicates, company/map pairings, actual specifications and CRM-only labels, selects the operational assignee and explicitly confirms final CRM import. Export is not import authorization.
